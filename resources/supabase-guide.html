Supabase is an open-source backend that gives your app a database, authentication, file storage, and more. We use it in this course to make your Todo++ app persist data across devices and users. This guide covers setup, features, and how to use it well with Cursor.
Getting Started
Setup Create Your Project
  1. Go to supabase.com and log in with GitHub
  2. Click New Project
  3. Name your project (e.g. “todo-plus-plus”)
  4. Generate a database password and save it to your password manager. The MCP connection uses OAuth (browser login) so it won't need this password. But if you ever connect directly to the database, you'll need it. If Cursor asks for it, paste it into your .env file, or into Chat if you're comfortable — just keep an eye on your account usage and billing, and set spending limits in the Supabase dashboard
  5. Pick the closest region to you
  6. Wait for the green light — your project is ready
Note: Provisioning can take 1–2 minutes. Wait for the dashboard to fully load before moving on.
Connect Connect to Cursor via MCP
Supabase MCP uses OAuth: Cursor opens your browser, you log in to Supabase and approve access. No manual tokens needed.
Paste this prompt into Cursor Chat to get set up:
Help me connect Cursor to my Supabase project using the MCP server. Use the hosted endpoint at mcp.supabase.com. It should open my browser to log in and approve access.
Verify it worked:
Ask Cursor Chat to list your tables. If it can see your database, you’re connected.
How it works: The MCP server uses OAuth 2.1 with dynamic client registration. You just log in through your browser, no personal access tokens or manual API keys needed.

Security Model
Important How Supabase Security Works
The anon key is designed to be public-facing. It’s safe to include in your client-side code.
Row Level Security (RLS) policies are the real security layer — they control what the anon key can actually do.
This is different from most API keys where exposure = danger. With Supabase, the anon key is meant to be exposed. RLS is what keeps your data safe.
Best Practice .env Files
Your .env file keeps your keys organized and out of your code. For Supabase, the anon key could technically be public, but .env is still good practice:
  • Keeps your code clean and readable
  • Makes it easy to switch between environments (dev vs production)
  • Some keys (like the service_role key) absolutely must stay private
Rule of thumb: anon key + RLS = your primary security.  .env = good organization.  service_role key = never expose.
2026 update: Supabase is rolling out publishable keys and revocable secret keys, replacing the old JWT-based anon/service_role model. Keys can now be scoped and rotated individually. Supabase also auto-revokes secret keys detected in public GitHub repos via GitHub Secret Scanning.
Pricing: What to Know
Free Tier Generous but Not Unlimited
Supabase starts free and covers this course. But know the limits:
  • 2 active projects: You can only have 2 projects running at once on the free tier. If you need more, pause inactive ones (paused projects don't count toward the limit). Your data is preserved when paused
  • Storage limits: 500 MB database, 1 GB file storage, 2 GB bandwidth, 500K edge function invocations, 200 concurrent Realtime connections
  • Gradual increases: more users, more data, more storage. You'll see usage approaching limits in the dashboard before anything changes
  • Sudden spikes: a leaked API key without RLS can let bots hit your database thousands of times. File storage costs can jump if you allow large uploads without limits
  • Auto-pause: free projects pause after 1 week of inactivity. Unpause to use them again
For this course: 2 active projects is enough. Enable RLS, keep an eye on the usage dashboard, and set billing limits. Pro plan ($25/mo) gives you more projects and resources for production use.

Tips
  1. Test with a private browser window. If your app shows data after refresh, it might be local storage, not the database. Open a private/incognito window or different browser to verify the database connection is real. This catches the most common “it works on my machine” issue with persistence.
  2. RLS before deployment. Enable Row Level Security before you share your app. Without it, anyone with the URL could read or modify your data. An unprotected Supabase database is fully accessible via the anon key.
  3. Start simple. You don’t need auth, realtime, and storage on day one. Get basic CRUD working first, then add features. Database → RLS → Auth → everything else.
  4. Check the dashboard. The Supabase Table Editor shows your data in real time. Use it to verify things are working before debugging code. If the data looks right in the dashboard, the problem is in your app code.
  5. The MCP connection is your superpower. Once connected, you can create tables, query data, and manage your database all from Cursor Chat without switching to the Supabase dashboard. Ask Chat to show your tables, run queries, or create new schemas — no SQL knowledge needed.
Relational vs Document Databases
What We Use Relational (Supabase/Postgres)
Tables with rows and columns, like a spreadsheet. Data is structured and connected through relationships.
  • Good for structured data with clear relationships
  • Good for complex queries across related data
  • Good when you know your data shape ahead of time
  • This is what we use in the course
Alternative Document (Firebase/MongoDB)
Collections of documents, like folders of JSON files. Data is flexible and can vary per document.
  • Good for unstructured or semi-structured data
  • Good for rapid prototyping
  • Good when your data shape changes frequently
  • More flexible, less structured
Bottom line: Both work. We use relational because it’s the most common pattern and Supabase gives us a lot of built-in features on top of it.
