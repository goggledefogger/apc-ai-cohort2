Personal Assistant Guide

Build an AI that knows you — from OpenClaw to Hermes and beyond
Cohort 2  |  April 2026
Student Resource
A personal AI assistant is an always-on agent that knows your preferences, manages your routines, and works on tasks while you sleep. It runs on your own hardware (a Raspberry Pi, an old laptop, a $5 VPS), connects to you through Telegram, WhatsApp, Slack, or another messaging app, and gets smarter over time. This guide covers the landscape — starting with OpenClaw (where Danny started), why practitioners migrate to Hermes, the knowledge patterns that make assistants actually useful, and the broader ecosystem of tools worth knowing about.
The Mindset Shift
Philosophy Chief Steering Officer
The biggest change is not technical — it is how you work. Instead of typing prompts and telling the AI what to do step-by-step, your job becomes setting direction, reviewing output, and removing blockers. The AI researches, codes, and monitors 24/7 — even overnight — while you approve or redirect.
Think of it as shifting from doing the work to managing a very capable (but literal) employee. You scale from what one person can accomplish in a day to what an army of agents can handle in parallel.
The Progression
Cursor / Claude Code → OpenClaw → Hermes → Whatever’s Next
Stage 1 IDE Assistants
Cursor and Claude Code live inside your editor. You drive, the AI assists. Great for building software, but you have to be at your desk with the project open.
  • You are in the loop for every action
  • Context is one project at a time
  • No memory between sessions (unless you set up CLAUDE.md)
Stage 2 Personal Assistant
An always-on agent that lives outside your editor. It knows your household, your schedule, your preferences. You message it from your phone and it works while you are away.
  • Runs 24/7 on your own hardware
  • Handles tasks across domains (home, work, media, errands)
  • Remembers past conversations and learns from them
  • Schedules recurring tasks and delivers results to your phone
Key shift: An IDE assistant helps you build things. A personal assistant helps you live your life. Different problem, different architecture.
OpenClaw
Platform Where Most People Start
OpenClaw is an open-source, highly extensible personal AI assistant framework that runs locally rather than in a walled-garden cloud. It operates continuously in the background with full system access — reading files, executing scripts, controlling your browser — and you interact with it through Telegram, WhatsApp, Discord, or Slack from your phone.
  • Architecture: session-based with a scheduled “heartbeat” cron job that lets the agent wake up, execute tasks, and proactively reach out without waiting for a prompt
  • Skills: governed by AGENTS.md, the core operational rulebook that dictates task execution, message patterns, cron standards, and error protocols
  • Model tiering: power users run free local models via Ollama or LM Studio (like Nomic embeddings) for memory search on-device, routing heavy reasoning to frontier models via API
  • Runs on: Raspberry Pi, Docker, cloud VMs — anywhere you can run Node
Strengths What OpenClaw Does Well
  • Unattended background automation: schedule web research, analytics scraping, finance audits, and morning briefings that run while you sleep
  • Gluing together disconnected systems: read a Slack thread, search a knowledge base, create a ticket, draft an outline, update a CRM — all autonomously
  • Large community and ecosystem — easy to find examples, kits, and help
  • Straightforward Docker Compose setup; good for learning agent architecture
Limitations Where OpenClaw Struggles
These are real problems you hit after running OpenClaw for weeks, not theoretical concerns:
  • Skill routing is fragile. AGENTS.md routing tables rely on the LLM to match requests to skills. Compliance runs 20–50% on some models. You end up writing hooks that inject skill files every turn as a workaround
  • Context compaction breaks on non-Anthropic models. On Gemini, compaction silently fails (compactionCount stays at zero). Your only option is a watchdog that hard-resets sessions at a token threshold, losing conversation state
  • Prompt drift across model families. OpenClaw was optimized for Claude. Running on GPT or Gemini requires “dual prompt stacks” — separate configurations per model family, with nightly sync scripts to keep them aligned
  • No cross-session search. Past conversations are opaque. You have to write custom scripts to search message history
  • Watchdog sprawl. Crontab entries, health-check scripts, loop watchers, error-reply services — each one a separate thing to maintain (~5 scripts just to keep things running)
  • Silent provider failover. When a provider goes down and OpenClaw fails over, it stays on the fallback silently until you manually reset the session config
  • Skill self-improvement is possible but not native. Recent versions allow agents to write skill files, but there is no built-in learning loop — you configure this yourself rather than getting it out of the box
  • Security risk: full local access means prompt injection from a web search or inbound email could execute harmful code. Mitigating this requires quarantining untrusted text, sandbox scanning, and deterministic redaction
Perspective: OpenClaw is a great learning platform. These limitations surface after you get serious about reliability and daily use. If you are just exploring the concept, it is a fine place to start — and the community will help you.
Hermes
Platform Built for the Problems OpenClaw Exposed
Hermes is a self-improving AI agent built by Nous Research. It operates from a single gateway process, interfaces through Telegram, Discord, Slack, WhatsApp, Signal, and a terminal UI, and runs on anything from a $5 VPS to a local machine. Unlike OpenClaw, it has a built-in closed learning loop — it gets better every time it completes a task.
Hermes includes a migration wizard (hermes setup) that auto-detects your ~/.openclaw directory and imports your SOUL.md, MEMORY.md, skills, command allowlists, and API keys into ~/.hermes/skills/openclaw-imports/.
  • Architecture: model-agnostic with explicit provider resolution (no silent failover)
  • Skills: LLM-powered matching with progressive disclosure + slash commands. Compatible with the agentskills.io open standard
  • Memory: FTS5 full-text search with LLM summarization across all sessions, plus Honcho dialectic user modeling
  • Scheduling: native cron with per-job skill loading, per-user delivery targets, and anti-recursion safety
  • Self-improvement: after completing complex tasks, the agent packages the workflow into a new skill that improves with use
  • Compute: six terminal backends (local, Docker, SSH, Daytona, Singularity, Modal) — heavy tasks run in cloud VMs instead of competing for Pi RAM
What Hermes Fixes
Six problems that required fragile workarounds in OpenClaw, solved natively in Hermes:
Problem OpenClaw Workaround Hermes Solution
Skill Routing AGENTS.md routing tables with 20–50% compliance. Bootstrap hooks injecting skill files every turn LLM-powered skill matching + progressive disclosure + slash commands. No routing table maintenance
Context Management Compaction broken on Gemini. Watchdog hard-resets sessions at 100K tokens, losing state Model-agnostic compression at 50% threshold with configurable retention. Works across providers
Session Search Custom Python scripts to search past conversations Built-in FTS5 full-text search with LLM summarization across all sessions

New Capabilities in Hermes
Compute Serverless Sub-Agents
Heavy research tasks run in cloud VMs (Modal, Daytona) that hibernate when idle and wake instantly. OpenClaw sub-agents all ran in-process, competing for your Pi’s RAM.
Knowledge Local RAG Search
Local embedding model (MiniLM, 22M params) with hybrid search over your knowledge base. Zero-cost semantic search on a Pi. OpenClaw’s vector search required Anthropic’s embedding API.
Messaging Per-User DM Topics
Telegram threads organized by domain (Media, Pets, Yard) with auto-loaded skills per topic. Ask about plants in the Yard thread and the gardening skill loads automatically. Multiple family members share one agent with profile isolation.
Operations Profile Export/Import
hermes profile export snapshots your entire assistant — skills, memory, config — in one command. Backup, migrate, or clone your setup. Replaces custom backup scripts.
Net effect: Delete ~10 watchdog/workaround scripts. Gain native cron, memory, skill routing, context compression. Unlock serverless offloading, local RAG, per-user topics. Maintenance burden drops significantly.
Knowledge Patterns
The difference between a chatbot and a personal assistant is how well it knows you. These two patterns determine whether your assistant starts every conversation from scratch or picks up where it left off.
Pattern Personal Context Portfolio
A structured set of ten markdown files that serves as an operating manual for any AI agent. Instead of repeating who you are every session, you hand the agent a portfolio and it already knows your role, preferences, and projects.
  • identity.md — one-page summary of who you are
  • role-and-responsibilities.md — what your actual weekly work looks like
  • current-projects.md — active workstreams and definitions of “done”
  • communication-style.md — how you prefer things written
  • preferences-and-constraints.md — hard rules agents must respect
  • domain-knowledge.md — specialized knowledge a general AI would not have
  • decision-log.md — real examples of how you make decisions
Key idea: Markdown-first, modular, portable across any AI system. Build it once, carry it everywhere.
Pattern LLM Wiki
Instead of retrieving fragments from a vector database, the agent actively maintains a structured, interlinked collection of markdown files — writing summaries, updating cross-references, flagging contradictions, and logging changes.
  • Three layers: raw sources (immutable originals), the wiki (LLM-generated summaries and syntheses), and the schema (rules for how the LLM maintains it)
  • index.md catalogs all content; log.md is an append-only change record
  • The wiki compounds over time — the more you use it, the more valuable it becomes
  • Works locally, no API costs for the knowledge base itself
Why not just RAG? RAG retrieves fragments. An LLM Wiki synthesizes knowledge. The agent understands relationships between facts, not just individual matches.
Platform Portability
Principle Don’t Get Locked In
Hermes supports standard plugins, the agentskills.io standard, and Model Context Protocol (MCP). If a better framework appears in six months, you swap the adapter instead of rebuilding from scratch.
This is the most important lesson from the OpenClaw-to-Hermes migration: your custom infrastructure should survive a platform change. Media pipelines, dashboards, Docker stacks, helper scripts — all of that carries over. The platform is the orchestration layer, not the whole system.
What stays the same in a migration: Your custom tools, media pipelines, dashboards, Docker services, and integrations. The platform gives them a better orchestration layer — it does not replace them.
The Broader Landscape
OpenClaw and Hermes are not the only options. The personal assistant space is evolving fast. Here are the other frameworks and tools worth knowing about.
Framework NemoClaw
NVIDIA-backed, open-source reference stack that runs OpenClaw agents inside the NVIDIA OpenShell runtime with enterprise-grade security. Adds layered protection, capability drops, and strict network policies to sandbox the agent. Solves OpenClaw’s prompt injection risk with guided onboarding and hardened blueprints.
Framework Phantom
Open-source, autonomous AI co-worker with root access to its own dedicated VM (Docker, databases, shell). Entirely self-evolving: after every conversation, Phantom reflects, proposes config changes, validates them with LLM judges, and rewrites itself. Exposes 17+ tools as an MCP server so other agents and IDEs can connect to it.
Platform agentOS
A runtime for complex, stateful agent workloads — from personal assistants to enterprise fleets. Supports programming agents with git/shell, background agents that persist state across crashes, multi-agent systems with shared file systems and messaging, and human-in-the-loop workflow automation.
Registry Journey Kits
Think npm for AI agents. Instead of prompting from scratch, point your agent at a Journey Kit and it downloads a complete workflow: skills, tools, database schemas, service integrations, and logged learnings. Designed for teams — agents share context without leaking private data.
Tool Littlebird
A desktop AI application that acts as continuous memory by privately reading your active screen and transcribing meetings. It already knows what you are working on across all your apps without manual integrations or catch-up prompts. Features include recall chat (“what was that link from this morning?”), automated meeting notes, and proactive routines. Privacy-first: ignores minimized/private windows, enterprise encryption, never trains on your data.
Anatomy of a Personal Assistant
1 Brain (LLM)
The language model that reasons and generates responses. Your assistant should work with multiple providers (Anthropic, Google, OpenAI) so you are not dependent on one company’s uptime or pricing. Use model tiering: run cheap local models through Ollama or LM Studio for embeddings and simple tasks, route heavy reasoning to frontier models via API.
2 Hands (Tools)
APIs, file system access, web browsing, smart home controls, messaging — anything the assistant can act on. MCP servers are the standard way to connect new tools. Journey Kits bundle tools with workflows.
3 Memory
How the assistant remembers. The best systems combine conversation history, semantic search (local RAG), the LLM Wiki pattern, and a Personal Context Portfolio. Without searchable cross-session memory, it is a chatbot with extra steps.
4 Skills
Reusable instructions for specific domains. Static skills are recipe cards you maintain. Self-improving skills are apprentices that get better every time they do the job. Look for platforms where the agent can write its own.
5 Scheduling
Recurring tasks that run without you. Morning briefings, plant care reminders, news digests, system health checks. This is the moment it stops being a chatbot and starts being an assistant — it does useful work while you are asleep.

Getting Started
  1. Pick your hardware. See the comparison above. Anything that can run Docker and stay on 24/7 works. Start with what you have. You can always upgrade later — your skills and config are portable.
  2. Choose a platform. Start with OpenClaw if you want the largest community. Start with Hermes if you want fewer workarounds from day one. Either way, you will learn the same fundamentals. The platform matters less than the skills and integrations you build on top of it.
  3. Set up a messaging interface. Telegram (via BotFather), WhatsApp, or Slack. This is how you will talk to your assistant from your phone. Telegram is the most popular choice — it supports group topics for domain separation, multi-user DMs, and has the best bot API. WhatsApp and Slack also work well depending on where you already live.
  4. Connect one LLM provider. Start with Google Gemini 2.5 Flash — best combination of power and value, with a free tier. See the “Choosing Your LLM” section for details and upgrade paths. You can add more providers later for redundancy. Do not over-optimize your model choice on day one.
  5. Build your Personal Context Portfolio. Start with identity.md and preferences-and-constraints.md. Add files as the assistant needs them. This is how the assistant stops being generic and starts being yours.
  6. Build your first skill. Pick something small and specific — a morning weather briefing, a grocery list manager, a plant watering reminder. One useful skill that runs every day teaches you more than ten skills you never finish.
  7. Add scheduling. Set up a recurring task so the assistant does something useful without you asking. This is the moment it stops being a chatbot and starts being an assistant.
The Development Loop
Key Insight Use Your IDE AI to Build the Assistant
It is tempting to set up a personal assistant and then only interact with it through Telegram or WhatsApp — messaging it tasks and seeing what comes back. That works once the assistant is mature, but early on you are missing half the picture.
The better approach: use Claude Code or Cursor, connected to your assistant’s machine via SSH, as your development companion. Now you have two layers working together:
  • Messaging (Telegram, WhatsApp, Slack): test the assistant the way a real user would. Send it a request, see if it responds correctly, check if the skill routes properly
  • IDE via SSH: look behind the scenes at what actually happened. Read the logs. Inspect the files the agent created. Check if the skill wrote to the right place. See why a cron job failed
This means your IDE AI is helping you build and debug the personal assistant — not just the assistant doing work for you. You can ask Claude Code to SSH into the Pi, read the agent’s logs, diagnose why a skill misfired, write a fix, test it by sending a message through Telegram, then verify the fix by checking the logs again. The full loop.
Message via Telegram → Assistant responds → SSH in via Claude Code → Inspect what happened → Fix and improve
Why this matters: Messaging alone shows you the output. The IDE shows you the process. Learning to read the logs and understand what the agent actually did — versus what it said it did — is the fastest way to build a reliable assistant.
Trust Framework
A personal assistant has access to your life. Deciding what it can do autonomously vs. what requires your approval is the most important design decision you will make.
Higher Trust Let It Run
  • Research tasks with no side effects (look up plant care, compare products)
  • Organizing and summarizing information you already have
  • Recurring reports and briefings
  • Managing lists, reminders, and your LLM Wiki
Lower Trust Review Before Acting
  • Anything that sends a message to another person
  • Purchases or financial transactions
  • Modifying shared systems (calendars, smart home)
  • Tasks where being wrong has real consequences
Rule of thumb: If the worst-case outcome of a mistake is “I have to redo it,” let the assistant run autonomously. If the worst case is embarrassment, lost money, or broken relationships, keep a human in the loop.
Security and Safety
A personal assistant has full access to your local machine — files, shell, browser. That power makes it useful, but it also makes prompt injection a real threat. If the agent reads a malicious web page or inbound email, it could be tricked into executing harmful commands on your system.
Framing The Lethal Trifecta
Any agent that combines all three of these is a serious risk, regardless of framework:
  1. Broad local access. The agent can read and write files, run shell commands, and control your browser.
  2. External communication. It can browse the web, send email, or make API calls outbound.
  3. Untrusted third-party skills. You installed community-contributed skills without reading them.
When all three overlap, a single malicious skill or prompt injection can exfiltrate your data. Community skill marketplaces (ClawHub being the largest) are a real supply-chain risk — skills pulled from public listings should be audited before install, not trusted by default.
Defense Multi-Layer Protection
Robust setups use a pipeline when ingesting untrusted content from the web or email:
  1. Quarantine. Downloaded content goes into an isolated sandbox. Deterministic code strips common injection markers (“ignore previous instructions”) The content never touches your main agent until it passes inspection.
  2. Frontier scan. A secondary model reviews the quarantined content for hidden malice — running in isolation with no system access. Worst case: the scanner reveals its own instructions, but it cannot harm your machine Think of it as a bomb-disposal robot: it can get tricked, but it is not holding the keys to your house.
  3. Deterministic redaction. Before any outbound message or API call, hardcoded rules strip PII, API keys, and financial data. Pre-commit hooks block key patterns from ever hitting repos or logs This layer is not AI-powered on purpose. Deterministic rules do not hallucinate.
Enterprise NemoClaw Security Model
For production-grade protection, NVIDIA’s NemoClaw runs OpenClaw inside the OpenShell runtime with:
  • Strict container security with capability drops and process limits
  • Network policies with operator approval flows and egress control — the agent is physically blocked from sending data to unauthorized servers
  • Messaging gateway isolated from the sandbox agent process
  • Guided onboarding wizard that configures security policies before the agent ever runs
Practical advice: You do not need NemoClaw to be safe. Start with the basics: do not give the agent access to your primary email or financial accounts until you trust the setup. Use a dedicated Google account for automation. Add redaction rules before you add web browsing.
Progression Graduate Permissions in Stages
Don't hand your agent the full toolkit on day one. Add permissions one service at a time, and escalate each service through a predictable ladder. Every stage is a chance to notice something weird before it becomes a problem.
  1. Stage 1 — One service, read-only. Pick one integration (calendar, email, your notes vault). Give the agent read-only credentials. Watch what it does with that access for a week before adding anything else.
  2. Stage 2 — Writes with confirmation. Keep the same single service. Enable writes, but require the agent to ask you before every write. Telegram-style "reply YES to send" is enough. You're building a sense for what kinds of writes it wants to make.
  3. Stage 3 — Strategic writes, narrow approval rules. Replace blanket confirmation with per-category rules. "Auto-approve calendar events under 30 minutes on my work calendar. Ask for anything else." The rules are yours to design — they come from what you saw in Stage 2.
  4. Stage 4 — Add the next service. New integration starts back at Stage 1. Never two new services at the same time. If something goes wrong, you know which one caused it.
Why this works: Agents don't fail randomly — they fail in patterns. Stage 2 is where you discover those patterns cheaply, before they're doing real things on your behalf. Stage 3 is where your review effort drops to near-zero because you've taught the rules.
Credentials Give Your Agent Its Own Identity
The single highest-leverage security move is treating your agent like a separate employee with its own credentials, not a second you. Three concrete pieces:
  • Dedicated email. A purpose-built agent email service like agentmail.to gives your agent its own inbox with structured subject routing and API access designed for machine use. Alternative: a dedicated Google account reserved for automation. Either way, never point it at your personal inbox.
  • Its own 1Password vault. Create a vault that only holds credentials your agent needs. Share it with no one. Scope secrets narrowly — if the agent only needs a Telegram token, do not give it your AWS root keys.
  • Accessed via the 1Password CLI (op). Secrets never sit in plaintext .env files. The agent calls op read at runtime and the CLI injects the secret into the process environment. If the agent is compromised, rotating a secret is one vault update instead of a repo rewrite.
Why this matters: The Replit, EchoLeak, and ClawHub incidents all share a root cause — the compromised agent had credentials it should never have been given. Scoped credentials turn a catastrophic breach into a rotatable inconvenience.
Managing Costs
An always-on agent that calls frontier models on every cron job will burn through your API budget fast. Token management is not optional — it is part of the design. And tokens are only half the bill: the other half is the power your hardware draws sitting idle all day waiting for something to do.
Vampire power: a 24/7 local agent on a laptop or Mac Mini draws real electricity even when it is doing nothing. For hobby use, a low-power Raspberry Pi 5 is dramatically cheaper to run than an always-on laptop. For heavy workloads, the greener move is to keep the gateway on the Pi but offload research bursts to serverless backends (Modal, Daytona, RunPod) that sleep when idle — you only pay for compute when the agent is actually thinking.
Strategy Model Tiering
Not every task needs an expensive model. Layer your costs:
  • Free / local: Ollama or LM Studio running Nomic embeddings for memory indexing and retrieval. Zero API cost
  • Cheap: Lightweight models for basic tool parsing, simple logic, and routine tasks
  • Frontier: Claude Opus, GPT-4, or Gemini Pro reserved exclusively for deep reasoning, writing, and complex tool use
Rule: If the task does not require reasoning, do not pay for a reasoning model.
Strategy Context Hygiene
The fastest way to blow your budget is a bloated context window sending irrelevant tokens on every call:
  • Domain topics: Telegram topics, Slack channels, or WhatsApp threads per domain. The agent only loads context for that thread, not everything
  • Automated pruning: A cron job that audits loaded files, trims duplicates, and clears prompt drift (~10% reduction every few days)
  • Space your cron jobs: Do not run five background tasks simultaneously. Stagger them overnight — analytics at 1 AM, CRM at 2 AM, briefing at 3:20 AM
  • Monitor usage: Check context capacity regularly (/status or /usage). Clear context or increase message expiration rates before hitting limits
  • Prompt caching: Use provider APIs that cache repeated context to reduce costs on stable system prompts
Choosing Your LLM
Just pick one provider and start. You can add more later. The best starting point for most people is Google Gemini 2.5 Flash — it is capable, fast, has a generous free tier, and costs very little when you do pay. As your assistant gets more complex, you can tier up to more powerful models or add alternatives.
Start Here Gemini 2.5 Flash (Google)
The best combination of power and value for getting started. Free tier available on Google AI Studio. When you pay, it is 8–10x cheaper and 3x faster than Pro models. 1M token context window. Native function calling support.
You will hit its limits fairly quickly with complex agent workflows — multi-step reasoning, long tool chains, and nuanced decisions can stumble. That is normal. When it happens, you have two paths: upgrade to a more powerful (and more expensive) model, or explore high-value alternatives.
Upgrade path: Gemini 2.5 Pro for harder reasoning tasks ($1.25/M input, $10/M output). Same API, just change the model name.
Once you outgrow Flash, here are the options — split between cloud APIs and local models you run yourself:

Recommendation Cloud API Tier
Start: Gemini 2.5 Flash for everything. Free tier, generous limits.
Add when needed: Claude Sonnet or MiniMax M2.5 for tasks where Flash stumbles. Route hard reasoning to Gemini 2.5 Pro or Claude Opus.
Access 200+ models: OpenRouter gives you one API key for almost everything. Hermes supports it natively.
Recommendation Local Model Tier
Embeddings (any hardware): Nomic via Ollama. Zero-cost memory indexing and semantic search.
Agent tasks on a Pi: Qwen 3.5 0.8B or 2B — native tool calling, small enough for limited RAM.
Agent tasks on a Mac Mini: Qwen 3.5 9B, GLM-4.7, or Gemma 4 26B MoE. Bigger models, better results.
Exploring: Gemma 4 for a general-purpose local model. Not agent-optimized but very capable.
Key principle: Do not over-optimize your model choice on day one. Start with Gemini 2.5 Flash, build your assistant, and upgrade the model when you hit a wall. The model is the easiest thing to swap later.

Lessons from Production
  1. Your custom infrastructure outlives any platform. Build pipelines, dashboards, and tools as independent services. The platform is the orchestration layer, not the foundation. When you migrate (and you will), everything you built independently carries over unchanged.
  2. Watchdog sprawl is a signal, not a solution. If you are maintaining five scripts to keep one system running, the platform is not solving your problem. Look for one that builds those capabilities in. Deleting workaround scripts is the best kind of progress.
  3. Self-improving skills change everything. A static skill is a recipe card. A self-improving skill is an apprentice that gets better every time it does the job. This is the difference between maintaining an assistant and growing one.
  4. Cross-session memory matters more than you think. An assistant that forgets last week’s conversation is a chatbot with extra steps. Searchable history with summarization is what makes it feel like it actually knows you. If you cannot search past conversations, the assistant is not learning.
  5. Test provider redundancy early. Your assistant will go down at the worst time if it only works with one LLM. Set up failover before you need it, and make sure failover is explicit, not silent. Silent failover is worse than loud failure. You want to know when quality drops.
  6. Per-domain topics keep context clean. Mixing gardening questions with media management in one thread degrades both. Separate threads or topics (Telegram topics, Slack channels) with auto-loaded skills keep the assistant focused. This is the personal-assistant equivalent of “one skill, one job.”
  7. Start with the Personal Context Portfolio, not the code. The fastest way to make any assistant useful is teaching it who you are. Technical sophistication without personal context produces generic results. identity.md + preferences-and-constraints.md takes 20 minutes and transforms every interaction.
